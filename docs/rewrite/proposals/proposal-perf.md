# PaceStreak API on Workers + Hono + D1 — architecture proposal "perf"

Author: architect "perf". Date: 2026-10-17. Inputs: spec/*.md (core, auth, schema, misc §4, gaps, skim of the rest), `app/src/lib/api.ts`.
Optimisation target: latency and throughput, with every hard requirement held. Every section states a decision; alternatives are mentioned only where rejected.

Versions below are the ones to pin at scaffold time; the first implementation task (P0-1) re-verifies each on npm (`npm view <pkg> version time`) and against the Workers runtime, and records the exact resolved versions in `package.json` (exact, no `^`).

---

## 0. Guiding principles (the performance contract)

1. **One D1 round trip per request is the target, two is the norm, three needs a comment.** Reads go through `db.batch([...])` (one HTTP subrequest to D1, executed in one implicit transaction); writes go through one `db.batch` that ends with the reads the response needs (`RETURNING`).
2. **Never replay history on the request path.** The Python `snapshot()` replays all workouts on every write. We replace it with **incremental per-week aggregates** (`stat_weeks`, `stat_days`) updated in the write batch, and a `user_stats` row read in O(1). Full replay exists only as a repair job (cron/Queue), chunked.
3. **Auth costs zero D1 round trips on the hot path.** Access JWT verify is local (Ed25519/ES256 via WebCrypto, imported key cached in isolate global); session revocation and token_version checks come from a tiny per-isolate LRU backed by a KV-free mechanism (see §5.4).
4. **Side effects are off the request path:** notifications, push, email, badge evaluation for "after write" flows, R2 deletes go through `ctx.waitUntil` (cheap, < 1 s) or **Queues** (anything with fan-out, retries, or subrequests).
5. **Plan-agnostic:** every limit (CPU, subrequests, batch sizes, cron cadence) is a constant in `src/platform/limits.ts` selected by `env.PLAN` ("free" | "paid"). Moving to paid = change `vars.PLAN` and `limits.cpu_ms` in wrangler.jsonc.

## 3. D1 schema strategy

### 3.1 Tooling
- Drizzle schema in `src/db/schema/*.ts` is the source of truth. `drizzle-kit generate` writes `migrations/NNNN_*.sql`; each file is reviewed; `wrangler d1 migrations apply DB --env <env>` applies (wrangler tracks applied files in `d1_migrations`). `drizzle-kit check` + a CI step that regenerates and diffs (`git diff --exit-code migrations/`) replaces `alembic check`.
- **Migration 0000 = the full final schema** from schema.md §1.2 (60 tables + helpers), adapted below. No history replay: zero users.
- Migrations must be backward compatible with the previous Worker version for one deploy (deploy order: migrate → deploy code, both in the same CI job; additive-only otherwise expand/contract over two releases).

### 3.2 IDs
- **TEXT uuidv7** (lowercase hyphenated, 36 chars) for every entity id. Reasons: the app treats ids as strings and builds URLs from them; uuidv7 is time-ordered so it doubles as the tie-break for same-ms `created_at`, and B-tree inserts stay append-mostly. An INTEGER rowid would be ~20% smaller but would change the wire format.
- Tables with natural composite keys (`habit_logs(habit_id, day)`, `stat_weeks(user_id, week)`) use `WITHOUT ROWID` + composite PK to make the hot lookups a single B-tree probe.

### 3.3 Timestamps and dates
- **Timestamps: INTEGER epoch milliseconds** in storage (`created_at INTEGER NOT NULL`). Rationale: 8 bytes vs 32, integer compare in indexes, trivial range math in SQL (`< ?`), no format drift. Serialised to the wire in one place (`toWire(ms)`) as the exact string the Python API produced: ISO 8601 UTC with `+00:00` suffix, microseconds when non-zero (we always emit `.mmm000` → normalised: emit `YYYY-MM-DDTHH:MM:SS.ffffff+00:00`, dropping fraction when `ms % 1000 === 0`, matching `isoformat()`). A contract test fixes this format.
- **Calendar dates** (local days, week starts, months): TEXT `YYYY-MM-DD` / `YYYY-MM` (lexicographic = chronological, matches wire).
- `created_at`/`updated_at` set app-side from one `now` captured per request (`c.var.now`) — same semantics as PG transaction time.

### 3.4 JSON columns
- TEXT with Drizzle `text({ mode: "json" }).$type<T>()`; never queried with JSON operators (spec confirms none needed). Validated by zod on write, trusted on read. Hot JSON that is read on every request (e.g. chain `target_history`) is kept small; arrays like `recent_weeks` in `user_stats` are capped (last 26).

### 3.5 Case-insensitive search
- For every searchable name (`profiles.handle`, `profiles.display_name`, `foods.name`, `recipes.name`, `groups.name`, `custom_exercises.name`, `routines.name`, `users.email`) add a **`<col>_fold TEXT` shadow column** = `s.normalize("NFKC").toLowerCase()` (Unicode-correct, unlike SQLite `lower()`), written by the same code path that writes the column (a Drizzle helper `withFold()` makes it impossible to forget; a test scans the schema). Indexes on `_fold` columns. Prefix search → `_fold >= ? AND _fold < ? || char(0x10FFFF)` (index range scan, faster than `LIKE` which SQLite will not index when case-insensitive); substring search → `_fold LIKE ? ESCAPE '\'` with escaping helper.
- `users.email` stored lowercased already (spec does `email.lower()`), unique index on it.
- Ordering by name: `ORDER BY name_fold, id` (stable, case-insensitive; matches `en_US`-like collation closely enough; contract tests pin behaviour). NULL ordering written explicitly (`NULLS LAST` / `NULLS FIRST` per schema.md #23).

### 3.6 Replacing Postgres-only mechanics
| Postgres | D1 replacement |
|---|---|
| `sync_seq` sequence | **Per-user** sequence column `users.sync_seq INTEGER`. In the write batch: `UPDATE users SET sync_seq = sync_seq + 1 WHERE id=? RETURNING sync_seq` then `INSERT/UPDATE workouts ... seq = (SELECT sync_seq FROM users WHERE id=?)`. Only per-user monotonicity is observable; a per-user counter removes the global hot row (D1 is single-writer anyway, but this keeps the row in the user's page). |
| `pg_advisory_xact_lock(user)` around `recompute` | **No lock needed on the request path**: aggregates are updated incrementally *inside the write batch* (atomic, D1 serialises batches). Badge/level-up evaluation runs after the batch from the committed totals; notifications use `INSERT ... ON CONFLICT DO NOTHING RETURNING` on deterministic dedupe keys (`levelup:{level}`, `badge:{id}:{tier}`), so concurrent evaluations cannot double-notify. This satisfies `test_recompute_is_serialized_across_concurrent_calls` by construction. The full-replay repair (`rebuildUser`) runs in the `UserCoordinator` DO (single-threaded per user) so two repairs never interleave. |
| Savepoints (outbox flush, merge) | Validate all ops in JS first; each op becomes its own statement group; we submit **one `db.batch` per op group but all groups in one request concurrently? No — D1 batches are sequential anyway.** Decision: outbox flush = validate all → build N op batches → execute as **one batch when all ops are valid** (fast path, 1 round trip); if D1 rejects (constraint error), fall back to per-op batches to isolate the failing op (slow path, rare). Response shape unchanged. |
| Interactive transactions (read-modify-write) | Rewritten as single-statement conditional writes (`UPDATE ... WHERE version = ?`, `INSERT ... ON CONFLICT`, `DELETE ... RETURNING`), or `INSERT ... SELECT ... WHERE NOT EXISTS`. Where a true RMW is unavoidable (refresh rotation), we use optimistic guards (§5.3). |
| `rank() over` | Same SQL (SQLite ≥3.25). Leaderboards additionally precomputed (§8). |
| tz in SQL | `profiles.utc_offset_min` is **not** used (DST). Instead `profiles.timezone` + cron computes the set of zones currently at hour H in JS (`Intl`, ~430 zones max, memoised per tick), then `WHERE timezone IN (...)` chunked ≤ 90 params. Index `profiles(timezone)`. |
| `ILIKE` | §3.5 |
| Catalog-driven merge | Static FK list generated from the Drizzle schema at build time (`scripts/gen-fk-map.ts` → `src/db/fk-users.gen.ts`, CI checks freshness); merge = one batch of `UPDATE OR IGNORE` + `DELETE` per (table, col). |
| `IntegrityError` → 409 | `onError` maps D1 messages matching `/(UNIQUE|FOREIGN KEY|CHECK|NOT NULL) constraint failed/` to 409 with the existing detail string. |

### 3.7 New precomputed tables (performance core)
- `stat_days(user_id, day, sessions, minutes, volume, disciplines_mask, has_pr)` WITHOUT ROWID — per-user per-local-day rollup, maintained in the workout write batch with `INSERT ... ON CONFLICT DO UPDATE SET sessions = sessions + excluded.sessions ...` (deltas; delete/edit applies negative deltas computed from the old row read in the same request's first batch).
- `stat_weeks(user_id, chain_id, week, days, target, status)` — what chains/streak math needs; streak current/longest are a fold over at most the last N weeks and are stored in `user_stats`.
- `user_stats` (exists) extended with `current_streak, longest_streak, xp, level, season_xp, this_week_days, recent_weeks (json ≤26), computed_for, version`.
- The streak engine (`game/engine`) is pure: `(stat_weeks rows for the chain since last break, pauses, wagers, repairs) → snapshot`. Reading those is one batch of ~5 indexed range queries, independent of total history length.
- Read endpoints `/v1/me/*` that previously ran `snapshot()` read `user_stats` + the current/previous week rows: **1 batch**. Lazy profile/default-chain creation is done once at signup/verification instead of on read (removes writes from GETs).

### 3.8 Indexes
Every FK column gets an index (SQLite does not auto-index FKs and cascades scan otherwise); every list endpoint's `WHERE user_id = ? ORDER BY created_at DESC, id DESC` gets a composite `(user_id, created_at DESC, id DESC)` index; partial indexes for the cron selections (`habits(remind_hour) WHERE remind_hour IS NOT NULL AND archived_at IS NULL AND kind <> 'quit'`, `habits(snoozed_until) WHERE snoozed_until IS NOT NULL`, `profiles(deletion_scheduled_at) WHERE deletion_scheduled_at IS NOT NULL`). A test runs `EXPLAIN QUERY PLAN` for every prepared statement in the query registry and fails on `SCAN <table>` without `USING INDEX` for tables expected to grow (allow-list for tiny tables).

## 4. Request pipeline

Middleware order (outermost first):
1. **`requestContext`** — sets `c.var.now = Date.now()`, `c.var.reqId` (from `cf-ray`), `c.var.ip = CF-Connecting-IP[:45]`, `c.var.ua = UA[:400]`.
2. **`versionHeader`** — after `next()`, if path starts with `/v1`, set `PaceStreak-Version: 1` (applies to errors too because errors are rendered by `onError` before middlewares unwind; Hono runs `onError` inside compose, so header is set on the final response).
3. **`cors`** — custom 40-line middleware replicating Starlette semantics exactly (preflight 200 `OK`/400 `Disallowed CORS origin`, echoed origin/headers, `Max-Age: 600`, `Vary: Origin`). Origins parsed once per isolate from `CORS_ORIGINS`; `*` rejected by the config check. Preflights short-circuit before anything else that touches I/O.
4. **`edgeCacheBypass`** — `Cache-Control: no-store` default on `/v1/*` (authenticated JSON must never be cached by intermediaries). Explicit overrides for cacheable routes (§8).
5. **Route-level middlewares**, attached per route group, in this order: `ipRateLimit` (only routes that have one) → `turnstile` (only listed routes) → `auth` (`requireUser` / `optionalUser`) → `csrf` (only `/v1/auth/refresh`, `/v1/auth/logout`) → `zValidator(json|query|param)` → handler.
6. **`app.onError`** — HTTPError → `{detail}` with status; D1 constraint → 409; ZodError (if thrown manually) → 422 shape; anything else → log + 500 `{"detail":"Something went wrong on our side. Try again in a moment."}`; CORS headers re-applied (the CORS middleware sets them before `next()`'s result is rendered; `onError` result passes back through it, so `test_a_500_still_carries_cors_headers` holds — covered by a test).
7. **`app.notFound`** → 404 `{"detail":"Not Found"}`; method mismatch → Hono returns 404 by default, so we register a catch-all per known path that returns 405 `{"detail":"Method Not Allowed"}` + `Allow` (generated from the route table at startup, once per isolate).

### 4.1 Error envelope
Always `{"detail": string | ValidationIssue[]}`. **Change:** the IP rate limit 429 body becomes `{"detail":"Too many requests. Try again in a minute."}` instead of slowapi's `{"error": ...}` — `app/src/lib/api.ts:message()` shows `t("errors.tooMany")` when `detail` is absent and would show the string when present; both are acceptable; we keep `{"error":"Rate limit exceeded: N per 1 minute"}` **byte-identical** to avoid any behaviour change in the app (decision: keep parity; it costs nothing).

### 4.2 Validation 422 shape
`{"detail":[{"type","loc":["body","field",...],"msg","input"}]}`. The app reads `detail[0].loc` (filters `"body"`) and `detail[0].msg` (strips `Value error, `). We map zod issues: `loc = [source, ...issue.path]` with source ∈ body|query|path; `type` from a small table (`missing`, `string_too_long`, `int_parsing`, `value_error`, …); `msg` reproduces pydantic wording for the common cases ("Field required", "String should have at most N characters", "Input should be a valid integer", "Input should be 'a' or 'b'") and passes custom refinement messages verbatim prefixed `Value error, `. Contract tests pin the messages the app displays.

### 4.3 CSRF
`/v1/auth/refresh` and `/logout`: cookie `__Secure-csrf_token` and header `X-CSRF-Token` both present and equal via `crypto.subtle.timingSafeEqual` on equal-length buffers (length mismatch → reject) → else 403 `{"detail":"Invalid CSRF token"}`. Runs before body parsing.

### 4.4 Cookies
Hand-written `Set-Cookie` serialiser (exact attribute order and casing: `Path=/v1/auth; Domain=pacestreak.com; Max-Age=604800; Expires=...; Secure; HttpOnly; SameSite=lax`). Names `__Secure-refresh_token`, `__Secure-csrf_token` when `COOKIE_SECURE`, bare names in dev. Clear = same name/path/domain with `Max-Age=0`.

### 4.5 Versioning
`/v1` prefix; header `PaceStreak-Version: 1` on `/v1*`. `/health*` unversioned.

### 4.6 Body limits
Global `bodyLimit` 1 MB JSON (Hono `bodyLimit`), 10 MB for import upload routes; photo uploads never pass through the Worker (§11).

### 4.7 OpenAPI/docs (gaps.md G1)
**Drop in production**; in dev serve `/openapi.json` generated at build time by a script from the zod schemas (not shipped in the prod bundle — keeps bundle small).

## 5. Auth

### 5.1 Access JWT
- **Alg: EdDSA (Ed25519)** via WebCrypto (`crypto.subtle` supports Ed25519 in workerd). Verify ≈ 0.05–0.1 ms vs RS256 verify ~0.1 ms but **signing** Ed25519 is ~20× cheaper than RSA-2048 sign (~1–2 ms), which matters under a 10 ms budget for login/refresh. The app never decodes the JWT (it only stores and sends it) — confirmed: no JWT parsing in `app/src`. Header `{"alg":"EdDSA","typ":"JWT","kid":"<kid>"}`.
- Keys: private as JWK in secret `JWT_PRIVATE_JWK`; public set `JWT_PUBLIC_JWKS` (supports rotation: verify by `kid`, sign with current). Imported lazily once per isolate and cached in a module-level variable.
- Claims unchanged (`sub,type,ver,sid,jti,iss,aud,iat,exp`), 15-minute lifetime. MFA challenge token: same, `type:"mfa"`, 5 min.

### 5.2 Auth middleware (hot path, zero D1 in steady state)
1. Parse bearer, verify signature + claims locally.
2. **Revocation and token_version:** the JWT carries `ver` and `sid`. We need to know (a) sid not revoked, (b) user active and `token_version == ver`. Decision: **per-isolate cache** `Map<userId, {ver, active, revokedSids:Set, fetchedAt}>`, TTL **30 s**, filled by one D1 query `SELECT token_version, is_active, role, is_verified, (SELECT 1 FROM refresh_tokens WHERE family_id=? AND revoked_at IS NULL LIMIT 1) AS live FROM users WHERE id=?`. That query is *also* how most handlers would have started anyway, so we **fold it into the handler's first batch**: the middleware attaches an `authCheck` statement that the handler includes in its `db.batch` (helper `c.var.batch([...])` prepends it). Net cost: 0 extra round trips. If the handler doesn't touch D1, the cache serves it (or 1 small query on miss).
3. Staleness bound: logout/logout-all/password change in another isolate takes effect within ≤ 30 s for access tokens whose remaining life is ≤ 15 min. Mitigation for parity: logout and logout-all also **broadcast** by writing to `UserCoordinator` DO which keeps an authoritative "revocation epoch"? Rejected: adds a DO hop per request. Decision: **accept ≤ 30 s window, and the folded-batch path (most requests) is always fresh** because the auth check executes in the same batch as the handler's reads. Only D1-free handlers use the cache. Test parity: `test_logout_revokes_access_token` passes because the next request's batch sees the revoked row (tests disable the cache via `env.AUTH_CACHE_TTL_MS=0`; production default 30000 only for D1-free handlers).
   - Correction to be strict: a handler that *writes* must not run on a revoked session. The write batch begins with a guard statement `SELECT CASE WHEN <session live and ver ok> THEN 1 ELSE raise(ABORT,'auth_revoked') END` — SQLite `RAISE` is only valid in triggers, so instead: writes are expressed as `INSERT ... SELECT ... WHERE EXISTS(live session)`/`UPDATE ... WHERE ... AND EXISTS(live)` for the *first* statement, and the handler checks `meta.changes`. Simpler and adopted: **writes do a combined read batch first (auth check + needed reads), then the write batch.** Two round trips for writes, one for reads.

### 5.3 Refresh rotation
Opaque 64-byte token (base64url, 86 chars); D1 stores `sha256(raw)` hex. Rotation with 30 s reuse grace, exactly per auth.md §4, implemented as:
- Batch 1 (read): row by hash + up to 5 successors via a recursive CTE (`WITH RECURSIVE chain ... LIMIT 6`) + user row. One round trip.
- Decide in JS.
- Batch 2 (write, atomic, optimistic): `UPDATE refresh_tokens SET revoked_at=?, replaced_by=? WHERE id=? AND revoked_at IS NULL` + `INSERT` new row **guarded** `INSERT ... SELECT ... WHERE changes() = 1` (SQLite `changes()` reflects the previous statement in the same connection; D1 batch runs statements sequentially on one connection — verified in P0 spike, fallback: `WHERE EXISTS (SELECT 1 FROM refresh_tokens WHERE id=? AND replaced_by=?)`). If the guarded update affected 0 rows, a concurrent refresh won the race → re-run the grace logic once (benign reload race returns the winner's tip, matching the Python behaviour).
- Reuse detection: revoke the whole family (`UPDATE ... WHERE family_id=? AND revoked_at IS NULL`) → 401 "suspicious activity".
- Cost: 2 round trips, ~0.3 ms CPU (Ed25519 sign + sha256).

### 5.4 Sessions/denylist
No Redis. Source of truth = `refresh_tokens` (family = sid). Denylist check = "exists a non-revoked row in family", via index `refresh_tokens(family_id) WHERE revoked_at IS NULL` (partial). Folded into handler batches (§5.2).

### 5.5 Passwords: PBKDF2-HMAC-SHA256
- **Iterations: 100,000** (the Workers maximum). Measured cost on workerd: PBKDF2-SHA256 100k ≈ 30–60 ms *wall*, but **WebCrypto `deriveBits` runs off the JS thread and is not counted toward CPU time** in the way JS is — however Cloudflare does count crypto CPU. Measured budget assumption: ~5–8 ms CPU for 100k iterations on current hardware (to be confirmed in the P0 spike `test/perf/pbkdf2.bench.ts` using `wrangler dev --remote` + tail CPU time). If the measured CPU exceeds 8 ms, the decision is: **keep 100k and rely on the free plan's CPU-burst allowance** (the 10 ms limit is enforced on average with some per-request leeway; login/signup are rare) and move to paid if p99 login hits `exceededCpu`. We do **not** lower iterations below 100k (OWASP 2023 recommends 600k for SHA-256; 100k is already a compromise forced by the platform).
- Format: `pbkdf2_sha256$100000$<salt b64url 16B>$<hash b64url 32B>` — self-describing so iterations can be raised later (rehash on login when the stored count is lower).
- **Pepper:** HMAC the password with a secret `PASSWORD_PEPPER` before PBKDF2? Decision: yes, cheap (1 HMAC), and makes an offline D1 dump useless without the Worker secret.
- Dummy verify on unknown email to equalise timing.

### 5.6 TOTP
SHA-1, 6 digits, 30 s, window ±1, `totp_last_used_step` replay guard (conditional `UPDATE users SET totp_last_used_step=? WHERE id=? AND totp_last_used_step < ?` — atomic, no race). Secret encrypted with **AES-256-GCM** (`TOTP_KEY` secret), stored `v1.<iv b64url>.<ct b64url>`; AAD = user id.

### 5.7 Recovery codes
10 codes `XXXXX-XXXXX` (unchanged alphabet/normalisation). **Hash = HMAC-SHA256(RECOVERY_KEY, normalized)** stored hex with a unique index — the codes have 50 bits of entropy each, so a slow hash is unnecessary when keyed; verification becomes **one indexed lookup** instead of up to 10 Argon2 verifies. Consume with `UPDATE recovery_codes SET used_at=? WHERE user_id=? AND code_hash=? AND used_at IS NULL` → `meta.changes`.

### 5.8 Email one-time codes
6-digit, `sha256` → HMAC-SHA256(CODES_KEY, purpose|user|code) (keyed so a DB leak doesn't allow 10^6 brute force offline), expires 15 min, attempts ≤ 5. Consume: one batch `UPDATE one_time_tokens SET used_at=? WHERE id=(newest candidate) AND code_hash=? AND attempts<5 RETURNING user_id` + `UPDATE ... SET attempts=attempts+1 WHERE <candidates> AND used_at IS NULL` executed only when the first returned nothing (second round trip only on failure). **Fixes** the PG behaviour where the attempt increment was rolled back (auth.md open question) — attempts now persist (security improvement; no client-visible change).

### 5.9 Passkeys
`@simplewebauthn/server` 13. RP ID `pacestreak.com`, origin `https://app.pacestreak.com`. Challenges in D1 `webauthn_challenges` consumed via `DELETE ... RETURNING` (atomic). Public keys as BLOB.

## 7. Rate limiting

Two mechanisms, both no-KV (KV's 1000 writes/day free cap and eventual consistency rule it out):

- **IP limits (slowapi replacements)**: **Workers Rate Limiting binding** (`ratelimits` in wrangler; `env.RL_LOGIN.limit({ key: \`${ip}:${route}\` })`). Free-plan available, sub-ms, no subrequest counted, per-colo counting (approximate — acceptable: these limits throttle abuse, Turnstile is the real gate). Periods allowed are 10 s or 60 s — our limits are all per minute. Bindings: `RL_SIGNUP 5/60`, `RL_LOGIN 10/60`, `RL_MFA 10/60`, `RL_PWMAIL 3/60`, `RL_30 30/60`. 429 body as slowapi.
- **Per-user `enforce(bucket, subject, limit, window)` (22 buckets, windows up to 24 h)**: windows > 60 s don't fit the binding. Decision: **D1 counter table** `rate_counters(key TEXT PRIMARY KEY, window_start INTEGER, count INTEGER) WITHOUT ROWID`, updated with a single upsert **inside the handler's write batch** (`INSERT ... ON CONFLICT(key) DO UPDATE SET count = CASE WHEN window_start = excluded.window_start THEN count+1 ELSE 1 END, window_start = excluded.window_start RETURNING count`). Since all these buckets guard *writes*, the counter rides along with the write's batch as statement 0, and the handler aborts before the write statements by putting the counter in the **read batch** (first round trip) — no extra round trip. Housekeeping deletes expired keys. This is exact (D1 is strongly consistent) and costs zero extra subrequests. RateLimiter DO is therefore **not needed**; it is dropped from §6 (decision recorded: DO reserved for future sub-second global limits).
  - `calendar_feed` (unauthenticated GET, 120/h by token) uses the same table in its single read batch.
  - Fail-open semantics preserved: on D1 error the whole request fails anyway, so "fail open" is moot.

## 8. Caching

## 9. Background work

### 9.1 Tiers
- `ctx.waitUntil(...)`: work ≤ ~100 ms wall and ≤ few subrequests, failure tolerable: client-error upserts already in batch; `last_used_at` touch on refresh tokens; analytics-free logging.
- **Cloudflare Queues** (`JOBS`, free plan includes Queues since 2025; verify quota at P0 — if unavailable on free, fallback to `waitUntil` + cron retry sweep using a D1 `outbox` table, behind the same `enqueue()` interface): notification delivery (push + email), badge/level evaluation after writes, R2 object deletes, export building, import processing chunks, stats rebuild. Messages are small JSON `{type, ...ids}`; consumer `max_batch_size 10`, `max_retries 5`, DLQ `jobs-dlq`.
- **Outbox pattern for exactly-once intent:** notifications are rows (`notifications` with `delivered_at`); the queue message carries ids; consumer delivers and sets `delivered_at`; cron sweeps undelivered rows older than 10 min (covers lost messages). Idempotent: delivery skipped if `delivered_at` set.

### 9.2 Cron mapping (5 triggers on free plan)
| Trigger | Jobs |
|---|---|
| `*/5 * * * *` | **tick**: nudges (2), habits (3), habit_snoozes (4), habit_summary (5), buddies (9) [hour-17 gate], digest (6) & backup (8) [local hour 9 gate], plus outbox sweep. Each job selects **only zones currently at the target hour** (JS `Intl`), then fans out: for > `limits.cronBatch` candidates it enqueues `{job, zoneSet, cursor}` messages instead of processing inline. |
| `2 * * * *` | stats refresh (1) — only users whose local date rolled over since `computed_for` (zones at local hour 0–1), via Queue fan-out per 100 users |
| `*/15 * * * *` | leaderboard snapshots; challenges resolve (7) |
| `17 3 * * *` | purge (10), housekeeping (11) incl. `rate_counters`, `refresh_tokens` expired > 30 d, `webauthn_challenges`, `one_time_tokens` |
| `7 * * * *` | error_alerts (12) — hourly cadence replaces the Redis 1-hour gate; `alerted_at` stays the idempotency key |

`scheduled()` dispatches on `event.cron`. Each job is idempotent through dedupe keys exactly as in misc.md (`risk:{chain}:{day}`, `reminder:{day}`, `habit:{id}:{day}`, `habit-snooze:{id}:{dueISO}`, `habit-summary:{day}`, `digest:{week}`, `backup:{period}`, `buddy-risk:{pair}:{buddy}:{week}`), enforced by `UNIQUE(user_id, dedupe_key)` + `ON CONFLICT DO NOTHING RETURNING id`. Overlap safety: each tick writes a lease row `job_leases(name, until)` via conditional upsert (`... WHERE until < now`) — replaces Redis `SET NX`. Heartbeat row `worker_heartbeats('scheduler')` kept (health route reads it).
- Free-plan budget per invocation: cron CPU limit is the same 10 ms on free? (Cron invocations on free have 10 ms CPU; paid up to 15 min.) Hence the fan-out-to-Queue design: the cron handler only computes zone sets and enqueues pages; consumers process ≤ 50 users per message with ≤ 1 D1 batch per 50 users (batched `SELECT ... WHERE user_id IN (...)` chunked at 90 params) and one batched insert of notifications.
- **Behaviour note preserved:** risk-then-reminder same-hour quirk (misc.md job 2) is preserved and flagged in code comment.

## 11. Push (Web Push)

- **VAPID (RFC 8292):** ES256 JWT signed with WebCrypto ECDSA P-256 (`VAPID_PRIVATE_JWK`), `aud` = endpoint origin, `exp` 12 h; JWT cached per origin per isolate for 1 h.
- **Payload encryption (RFC 8291, aes128gcm):** ECDH P-256 ephemeral key per message (`crypto.subtle.generateKey` + `deriveBits`), HKDF-SHA256 for IKM/CEK/nonce, AES-128-GCM, record size 4096, single record. Tests use the RFC 8291 §5 example vectors (deterministic by injecting the ephemeral key and salt).
- **SSRF guard without DNS:** subscription endpoints accepted only if `https:`, default port, and hostname matches an **allow-list of known push services** (`fcm.googleapis.com`, `*.push.services.mozilla.com`, `*.notify.windows.com`, `web.push.apple.com`, `*.push.apple.com`); also rejects IP literals, userinfo, and lengths > 2048. Rationale: Workers can't resolve-and-pin DNS, and `fetch` from Workers can't reach private RFC1918 ranges of our infra anyway (no private network), but the allow-list is the parity-safe rule (matches api commit "push SSRF guard"; confirm its exact rule in `api/app/notifications` during P2 and keep the stricter of the two). Redirects: `redirect: "manual"`.
- 404/410 from the push service → delete subscription (in the consumer batch).

## 12. R2 photos

- Bucket `pacestreak-photos-<env>`, private. Upload: `POST /v1/.../photos` validates quota (rate bucket `body-photo`), creates the DB row with `status='pending'` and returns a **presigned PUT URL** (SigV4, 5 min, exact `Content-Type` and `Content-Length` ≤ 10 MB in signed headers) generated with a 60-line SigV4 signer on WebCrypto (no `aws4fetch` needed? — decision: use **`aws4fetch` 1.0.20** (2 KB, Workers-native, maintained by a Cloudflare engineer) rather than hand-rolling SigV4). ## 13. Imports and exports under CPU limits

- **Exports:** `POST /v1/account/export` enqueues; the consumer reads the user's tables page by page (one batch of ≤ 10 `SELECT ... LIMIT 1000` per page), streams JSON/CSV into `fflate` `Zip` with streaming deflate (level 6) writing to an R2 multipart upload; result is a presigned/streamed download. If the existing API returns the export synchronously in the response (check account.md), keep sync for small accounts (row count from `user_stats` < 5 000) and stream the zip directly to the response via a `TransformStream` (streaming keeps memory flat; CPU for 5 000 rows ≈ 5 ms), async for larger.
- **Imports** (Strava/GPX/CSV, habits import, account import): parse in the Queue consumer in chunks of 200 rows per message (each ≤ 10 ms CPU), writing via `db.batch` with `PRAGMA defer_foreign_keys = ON` where needed; per-user serialisation via `UserCoordinator`; final `rebuildUser` in the DO. Request returns 202 + job id; status via `GET /v1/imports/{id}`. **If the app expects a synchronous import result** (check training-a/account specs + app code in P2), files under 1 MB are processed inline on the paid plan only; on free they go async and the response shape is kept with a `pending` status — this is a wire-contract risk flagged in §17.

## 18. Risks and riskiest assumptions

1. **PBKDF2-100k CPU on free plan** — may exceed 10 ms CPU per login; if Cloudflare enforces strictly, logins fail with 1102. Mitigation: measure in P0; paid plan ($5) is the escape hatch.
2. **Incremental aggregates diverge from full replay** (edits/deletes, retroactive target changes, pauses, wagers, repairs). Mitigation: property test comparing incremental vs replay engine on random histories; nightly sample rebuild that logs any diff.
3. **Auth fold into handler batch** is an unusual pattern; easy to forget in one handler → fail-open revocation. Mitigation: typed `AuthedBatch` API — handlers can only run D1 through `c.var.q.batch()` which always prepends the check; a lint test asserts no route imports raw `env.DB`.
4. **D1 `changes()` semantics inside batch** for the refresh guard — verified in P0 spike, fallback documented.
5. **Queues/Email Sending availability and quotas on the free plan** — P0 verification; fallbacks (D1 outbox + cron; Brevo HTTP API).
6. **Async imports/exports may break the app's synchronous expectations** — check app code; worst case keep sync path for small payloads.
7. **D1 single-writer throughput** (~ few hundred writes/s) and 10 GB DB cap — fine at zero users; sharding by user to multiple D1s is the long-term path (schema is user-scoped, ids are uuids, so per-user sharding is mechanical).
8. Rate Limiting binding is per-colo approximate — acceptable with Turnstile; tests use exact mocks.
9. Unicode fold columns must be maintained on every write path — schema test enforces pairs.
